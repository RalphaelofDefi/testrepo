# SmartFinance — Explanation of System Diagrams

This document explains, in narrative form, the two core design diagrams of the SmartFinance intelligent web-based expense tracker: the **Entity Relationship (ER) Diagram** and the **Use Case Diagram**. Both descriptions are derived directly from the implemented system — the MySQL schema (`backend/database/schema.sql`) and the application logic (`backend/public/index.php`, the cron jobs, and the React client).

---

## 1. Entity Relationship Diagram — Explanation

The database design of SmartFinance is built around a single central entity, **users**, from which every other entity in the system ultimately derives its meaning. A user represents a registered account holder and carries the identity and financial baseline of the application: a unique username and email, a securely hashed password, a configurable starting balance, and a preferred currency. Because the entire platform is personal-finance oriented and does not implement any administrative role, the user entity acts as the hub of the schema — ten of the eleven tables are connected to it through foreign keys, and deleting a user cascades outward, removing every trace of that person's activity from the system.

Radiating from this hub are the two entities that carry the core financial payload. The **transactions** table is the unified ledger of the application: rather than maintaining separate income and expense tables, every money movement is a single row distinguished by a `type` column that may hold either `income` or `expense`. Each transaction is bound to exactly one owner, carries an amount, a category, an optional description and date, and may hold a JSON collection of tags. The **goals** entity models the savings-goal feature, and it is considerably richer than the transaction entity because goals are time-based and partially automated. A goal declares a target amount and a deadline, tracks how much has been accumulated so far, and defines a savings plan through its frequency (daily, weekly or monthly), its scheduled amount (the sum deducted in each period), the next and last deduction dates, and a missed-contribution counter. Its status column walks the goal through a small lifecycle — active, completed or paused — while a derived progress percentage is maintained for immediate display.

The automation of these goals produces the most interesting relationship in the schema. When the system deducts money for a goal — whether the daily cron job fires or the user contributes manually — it does not modify the balance directly. Instead it inserts an **expense transaction** whose category is the reserved value `Savings Goal` and whose description names the goal. This design decision means the balance formula (starting balance plus income minus expenses) needs no special cases, but it also means that goals and transactions are linked *logically* rather than structurally: there is no foreign key between them, only a shared convention. In the ER diagram this appears as a dashed line, deliberately weaker than the solid constraint lines elsewhere, and it is an important honesty point about the schema — the database does not enforce the connection, the application does.

Every consequence of that automation is recorded in **goal_notifications**, which is the only table in the schema that receives two foreign keys. Each notification belongs simultaneously to a user (who will read it) and to a goal (which caused it), and it captures an event type — a successful deduction, an insufficient-balance failure, a completed goal, or an approaching deadline — together with a human-readable title and message, the amount involved, and a snapshot of the user's balance at the moment the event occurred. This snapshotting is deliberate: notifications are historical records, and the balance shown in them must not change after the fact. The `is_read` flag supports the frontend's fetch-and-clear pattern, where retrieving unread notifications also marks them as read.

The intelligence layer of the system leaves its own footprint in the schema. The **ai_logs** table records every interaction with the HuggingFace-hosted Meta-Llama-3-8B model — the engineered prompt that was sent, the response that came back, the response time, an estimated token count, and a success/error/timeout status. This table quietly serves three masters at once: it is an audit trail of AI behavior, the storage mechanism for chat history (the conversation context passed to subsequent prompts is read back from it), and the rate-limiting ledger (the service counts a user's AI calls within a rolling window before deciding to refuse a request). Meanwhile, **monthly_summaries** stores the precomputed financial report that the monthly cron job generates for each user — totals of income, expenses and net savings, the transaction count, the largest spending category, and, when AI features are enabled, a serialized JSON insight produced by the model. Its unique constraint on the pair of user and summary month guarantees one report per user per month.

The remaining entities form the security and preference perimeter. **user_sessions** implements the revocable bearer-token scheme: every login mints a token and records it here alongside the IP address, user agent and expiry, and every subsequent API call verifies that its token still exists and has not expired — which is what makes "sign out this device" and "sign out all devices" possible. **user_otps** holds one-time passcodes for the sensitive flows (password reset, email change, password change), recording the purpose, the code, an expiry timestamp, the number of failed attempts (the code self-destructs after five), and a JSON payload for contextual data such as the pending new email address. **user_settings** is the schema's only strict one-to-one relationship: its primary key is simultaneously its foreign key to the user, which structurally guarantees that a user can never have more than one settings row. It stores the currency preference, the savings automation configuration (frequency, deduction day, on/off switch), the AI enablement toggle, and two JSON documents holding the granular notification and dashboard-widget toggles. Finally, two tables exist purely for operations: **system_logs**, which records application-level events and survives user deletion by nulling its user reference instead of cascading, and **rate_limits**, which indexes a user id but notably carries no actual foreign-key constraint — another intentional soft reference, since throttling must keep working even if the referenced account disappears.

Three database **views** complete the picture as virtual, derived entities. `user_financial_summary` joins users to transactions and exposes the canonical balance formula; `user_category_breakdown` aggregates spending per category with count, average, minimum and maximum; and `user_monthly_trend` groups transactions into calendar months to expose income, expense and net savings over time. None of them store data — they exist so that the dashboard's heaviest queries are pre-shaped at the database layer.

Taken as a whole, the ER diagram describes a system where one user entity fans out into a ledger (transactions), a plan (goals), an event feed (notifications), an intelligence log (ai_logs), a reporting archive (monthly summaries), a security envelope (sessions, OTPs) and a preference record (settings) — with the goals-to-transactions funding path and the rate-limit reference kept as explicit, dashed "soft" links to show where behavior is defined by the application rather than enforced by the database.

## 2. Use Case Diagram — Explanation

The use case diagram of SmartFinance recognizes five actors, only two of them human. On the left stands the **Guest**, an unauthenticated visitor who is deliberately restricted to a small entry area of the diagram: registering an account, logging in, requesting a password reset, and completing that reset. On the same side, drawn larger and with a double outline to mark it as the primary actor, stands the **User** — the authenticated account holder who owns everything the system can do. The right side of the diagram is occupied by three non-human actors. The **Scheduler (Cron)** is a system actor that fires on a timetable rather than through the interface, driving the automated savings engine. On the far right, outside the system boundary and rendered as clouds because they are external services, sit the two secondary actors: the **HuggingFace LLM (Meta-Llama-3-8B)**, which receives engineered prompts and returns financial analysis, and the **SMTP Mail Server**, which delivers every email the system produces. Modeling these as actors — rather than hiding them inside the system — accurately reflects that SmartFinance's signature features depend on outbound integrations whose availability it does not control.

Within the system boundary, the use cases cluster into six visible groups. The **authentication cluster** contains registration and login for the guest, plus logout for the user; it is guarded in depth, with password hashing on the way in and revocable session tokens on the way out. The **transaction cluster** is the operational heart: viewing, recording, editing and deleting income and expense entries. It is worth noting that recording a transaction is a *single* use case — the system intentionally unifies income and expense into one form distinguished by a type field, rather than modeling them as separate use cases. Every one of these use cases is quietly protected: the actor reaches them only through an authenticated session, and ownership is verified on every edit and delete.

The **goals and savings cluster** is where the system's distinctive behavior lives. The user can create a goal — and creation «includes» the computation of the scheduled amount, derived automatically from the target, the deadline and the chosen frequency — as well as edit, delete and observe progress. Making a manual contribution is modeled with two extension points that capture the business rules: if the balance cannot cover the amount, the flow extends into an insufficient-funds alert, and if the contribution completes the target, it extends into marking the goal completed and congratulating the user. The same two extensions are reused by the **background automation cluster**, where the Scheduler actor drives the processing of due deductions. This reuse is the diagram's most important structural statement: automated and manual savings obey the same rules, fail the same way when funds are short, and celebrate the same way when a goal completes. The cron actor additionally triggers deadline reminders for goals due within seven days and the monthly summary generation, both of which reach out to the mail server, and the summary job further engages the LLM when the user has AI features enabled.

The **AI intelligence cluster** — chat with the assistant, dashboard insight, and per-goal advice — is intentionally drawn in a prominent color because it is the project's differentiator. Each of these use cases connects to the HuggingFace actor as its secondary participant and is constrained by two behaviors that the diagram renders formally: an «include» relationship to a rate-limit check, which protects the external API from abuse, and an «extend» relationship with the guard condition `ai_enabled = false`, which returns an error when the user has switched AI features off in their preferences. In other words, the AI features are not unconditionally available, and the diagram says so explicitly rather than leaving it as an implementation detail.

The **settings and account cluster** gathers the user's self-service administration: managing preferences (currency, savings frequency, deduction day, notification toggles, dashboard widgets), changing email, changing password, uploading a profile picture, managing active sessions, exporting data as CSV, reporting a problem to support, and deleting the account. The sensitive operations among these are modeled with «include» relationships to verification steps — both email change and password change «include» sending and verifying an OTP, password change additionally verifies the current password, and account deletion verifies the password before cascading deletion across every owned record. One further «extend» captures a development convenience with production implications: when SMTP is not configured and the application is not running in production, the OTP flows extend to return the code directly in the response so the flows remain testable without a mail server.

Finally, the diagram expresses the security boundary without drawing a wall around anything. All of the viewing use cases carry an «extend» relationship to a "redirect to login" use case whose condition is an expired or revoked token — so an intruder who somehow reaches a protected view is not shown data but a redirect. This is why the Guest actor has no lines crossing into the authenticated clusters: the boundary between Guest and User is not positional, it is behavioral, enforced by the session-verification logic that every protected use case begins with.

Read as a whole, the use case diagram describes a system in which a single primary actor manages a personal financial ledger and savings plan, an invisible clock drives the same savings plan on the actor's behalf under the same rules, and two external services — one intelligent, one communicative — extend what the system can do, while the include and extend relationships encode the verification, rate-limiting, failure and celebration behaviors that make the whole thing coherent.
